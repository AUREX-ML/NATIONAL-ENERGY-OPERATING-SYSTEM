# Open Source, IP & Intellectual Capital

## Purpose

This document governs how the institution creates, uses, protects, shares and compounds software, research, standards, data models, documentation, operational knowledge and other intellectual assets.

> Open source is not the absence of intellectual-property governance. It is an intentional method of governing intellectual property.

## Intellectual Capital

Institutional intellectual capital includes source code, architecture, algorithms, data models, protocol mappings, research, datasets, standards, test suites, documentation, ADRs, deployment experience, operating knowledge, relationships, brands, inventions and protected know-how.

It is considered across human capital, structural capital and relational capital. Critical knowledge should progressively move from individual memory into durable structural capital without eliminating professional judgment.

## Intellectual Asset Governance

Material assets should retain an ID, type, origin, owner, rights/license, classification and lifecycle status. Provenance records who created the asset, when, under which project, using which prior work and subject to which licenses or contribution rights.

## Open-Source Strategy

Open source supports interoperability, transparency, adoption, collaboration, auditability, local capacity, reduced vendor lock-in, reproducible research and ecosystem formation.

Shared infrastructure interfaces should favor open standards. Openness does not override privacy, security, contractual obligations, personal/customer data protections or critical-infrastructure restrictions.

## Repository Governance

Repositories have an explicit purpose, owner, maintainers, license, contribution policy, release policy, security contact and lifecycle state. States may include experimental, active, maintenance, deprecated and archived.

Consequential changes require peer review and automated validation. Merge authority is limited, auditable, revocable and role-based.

## Contribution Governance

`CONTRIBUTING.md` defines issues, proposals, branches, commits, pull requests, tests, documentation, review, sign-off, licensing, security reporting and community conduct.

Device integrations require supported model/firmware information, protocol source, mappings, tests, sample configuration, limitations, conformance evidence and documentation—not code alone.

Research contributions require question, method, data/data-access description, result, limitations, reproduction information and licensing.

## Dependencies & Supply Chain

Material dependencies record source, version, license, purpose, maintainer, security status and update policy. Third-party code is reviewed for provenance, license compatibility, maintenance and security before adoption. Software Bills of Materials should be produced where appropriate.

## Upstream & Forks

Generic improvements should be contributed upstream where strategically appropriate. Forks require a documented reason, owner, divergence, patch set, synchronization strategy and exit plan. Permanent divergence creates maintenance, security, testing, upgrade and knowledge debt.

## Documentation as Infrastructure

Policies, standards, specifications, procedures, runbooks, ADRs, catalogues, registers and guides are distinct artifact classes. Significant documentation should have an owner and lifecycle state. Authoritative terminology belongs in a governed glossary.

## IP Governance

Relevant IP classes include copyright, patents, trademarks, trade secrets, database rights where applicable and contractual know-how. Potential inventions require an explicit decision on patenting, publication, controlled disclosure or another strategy before consequential public disclosure where rights may be affected.

Research partnerships should distinguish background IP, foreground IP, joint IP, licensing, publication and commercial rights. Dataset, software, model, schema and brand rights are governed separately where appropriate.

## Security Disclosure

Security vulnerabilities use a private reporting and coordinated-release path rather than ordinary public issue channels. Security-sensitive information may be temporarily restricted while remediation is prepared.

## Knowledge Continuity

Bus-factor risk is mitigated through documentation, pairing, review, runbooks, training and ownership redundancy. Knowledge transfer is a controlled process, particularly when ownership changes or key contributors leave.

## Core Laws

1. Open source is governed intellectual property, not ownerless technology.
2. Significant intellectual assets retain provenance, ownership, rights and classification.
3. Open standards are preferred for shared infrastructure interfaces.
4. Every maintained repository has an explicit purpose, owner, lifecycle and license.
5. Third-party code is reviewed for provenance, security and licensing.
6. Generic improvements should move upstream where strategically appropriate.
7. Every maintained fork has an owner, justification, sync strategy and exit plan.
8. Documentation is part of the infrastructure.
9. Critical knowledge must become institutional rather than remaining exclusively personal.
10. Open-source sustainability requires maintainers, governance, documentation, security and funding—not code alone.
