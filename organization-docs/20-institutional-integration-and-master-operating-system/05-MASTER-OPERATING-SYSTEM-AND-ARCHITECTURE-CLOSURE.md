# Session 5 — Master Operating System & Architecture Closure

## Purpose

Close the 20-domain organizational architecture by defining the institutional control layer that connects purpose, governance, people, technology, capital, operations, evidence and learning.


The Master Operating System must continuously answer:

- Why do we exist?
- What are we trying to achieve?
- What stage are we actually at?
- What are we building now?
- Who owns what?
- Who may decide?
- What resources exist?
- What risks and controls exist?
- What is operating or failing?
- What evidence exists?
- What must happen next?

## MOS Layers

- **MOS-0 — Purpose:** vision, mission, founder thesis, institutional principles and long-term outcome.
- **MOS-1 — Governance:** authority, policy, risk, decision rights, accountability, compliance, control and escalation.
- **MOS-2 — Strategy:** objectives, outcomes, portfolio and resource allocation.
- **MOS-3 — Execution:** portfolio → program → project → work package → deliverable → capability.
- **MOS-4 — Operations:** capability → service → operation → monitoring → maintenance → support → recovery.
- **MOS-5 — Assurance:** requirement → control → execution → evidence → assurance → finding.
- **MOS-6 — Learning:** result → measurement → lesson → decision → change → standardization.

## Architecture Change Control

The 20-domain architecture is a governed baseline, not an immutable structure. A domain should only be created when a capability has distinct purpose, accountability, a significant artifact set, significant dependencies and durable institutional value.

A missing document is not automatically a missing domain.

Domains may later be merged, split, superseded or retired with architecture history preserved.

## Architecture Baseline

Completion establishes **Organizational Architecture v1.0 — 20 Domains — Baseline Complete**.

The baseline freezes, for controlled evolution:

- Domain map
- Domain purposes
- Domain boundaries
- Master principles
- Core artifact requirements
- Integration model

## Architecture Completion vs Organizational Completion

```text
ARCHITECTURE COMPLETE ≠ ORGANIZATION COMPLETE
```

Architecture completion means the blueprint now defines what must exist. Implementation must determine what actually exists, what is missing, what is stale, what is duplicated and what is currently required.

## Master Operating Controls

The institutional baseline requires that purpose is explicit; strategy traces to purpose; work traces to strategy or governed need; domain boundaries and ownership are explicit; critical dependencies are visible; authoritative registers exist; current and target state remain distinct; gaps are prioritized; work intake is governed; decision and escalation routing follow authority and consequence; critical exceptions remain visible; health remains distinct from maturity; systemic risk is evaluated across domains; shared capabilities are reused; local autonomy is preserved where appropriate; continuity and succession cover critical functions; institutional memory survives personnel change; architecture changes are governed; implementation remains stage-aware; domains are not confused with departments; and automation supports rather than silently replaces institutional authority.
